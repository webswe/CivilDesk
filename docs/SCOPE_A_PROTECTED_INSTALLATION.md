# Scope A protected installation foundation

This document describes a **future supervised deployment**, not an active approval. Production `APPROVED_FROZEN` remains `None`; the only prospective D2L-CLI command is `auth capabilities --json --contract-version 1`. No real credential, account, browser login, or academic retrieval operation is authorized.

## What is implemented

- The default NSIS configuration remains `currentUser`. Select the separate `src-tauri/tauri.protected.conf.json` overlay at build time with `npm run tauri build -- --bundles nsis --config src-tauri/tauri.protected.conf.json`. It requests Tauri NSIS `perMachine`, keeps `com.webswe.civildesk`, and disables updater artifacts. `npm run check:protected-install` checks these build-time properties. An installer built with this overlay must still pass VM acceptance before distribution.
- The frozen CLI is a **separate component**, never an NSIS payload of an ordinary CivilDesk upgrade: proposed root `C:\Program Files\CivilDesk D2L-CLI\3ce1648\`. Proposed independent manifest: `C:\ProgramData\CivilDesk\Trust\trusted-d2l-3ce1648-manifest.json`. The development candidate directory is only an input source.
- `scripts/verify-protected-package.mjs` checks explicit manifest, source, executable digest, canonical root, 306-file count, 139,599,398-byte inventory, hashes, missing/extra files, reparse paths, and hard-link count. Its expected identities are supplied at invocation; it does not activate trust. Verification must be repeated **after** privileged staging.
- `scripts/verify-protected-acl.ps1` inspects owners, DACLs, ancestors, files, and current-token effective access without changing permissions. It fails on suspicious rights. This cannot prove effective access for every local account or every hard-link route; an elevated disposable VM test with separate ordinary-user accounts remains mandatory.
- `scripts/inspect-scope-a-firewall.ps1` checks the effective firewall policy store for an outbound block at an exact installed executable path, all profiles, all remote addresses, and all protocols, and requires all three firewall profiles enabled. It neither creates a rule nor supplies a sandbox. The deployment operator must separately establish that policy ownership is administrator controlled and prove enforcement with an offline test process.
- `scripts/inspect-installation-transition.ps1` reports registered HKCU/HKLM CivilDesk installations and flags conflicting scopes or machine roots. It does not uninstall, migrate, or detect every portable copy or another user's HKCU installation.

## Proposed ownership and ACL policy

Use an elevated, reviewed installer for the CivilDesk application in `C:\Program Files\CivilDesk\`; install the versioned CLI separately under `C:\Program Files\CivilDesk D2L-CLI\3ce1648\`; store the independent manifest under `C:\ProgramData\CivilDesk\Trust\`. SYSTEM/Administrators (or a managed installer service) own and control writes, deletes, ACL changes, and ownership changes on those files and their relevant ancestors. Ordinary Users receive only read/execute and directory traversal as needed. Check effective rights on each directory and file, including delete-child on parents, inherited grants, and alternate writable hard-link routes. Do not grant Users or Authenticated Users Modify, Full Control, WRITE_DAC, WRITE_OWNER, Delete, or Delete Child. Confirm each actual ACL under an unelevated user token and independently as administrator in a disposable VM. Program Files and ProgramData alone do not prove these properties.

Use versioned package roots and a separately controlled trust-manifest path. Never allow a routine CivilDesk uninstall to remove the independently installed CLI. Stage into a private elevated directory, reject reparse points and unexpected links, validate every file, atomically place the reviewed version, then rehash and validate ownership/ACLs at the final paths. Fail closed if any item is missing or changed. Existing runtime hash verification still has a verification-to-launch race and job attachment occurs after process creation; ACLs reduce exposure to ordinary users but cannot defeat administrators, compromised installer services, kernel access, or all child-process behavior.

## Safe transition from current-user installs

The current bundle is per-user; the protected overlay is per-machine. Do not assume NSIS upgrades HKCU to HKLM. In a disposable Windows VM, test fresh HKLM install, HKCU-only install plus HKLM install, duplicates, both uninstall orders, shortcut ownership, registry entries, rollback, and versioned upgrade. Block or explicitly supervise conflicting production installations; never silently uninstall the HKCU copy. Keep CivilDesk Acceptance (`com.webswe.civildesk.acceptance`) separate. Preserve the production identifier so per-user Tauri app data, WebView2 profile, settings, Notion credential identity, and project-file references remain associated with the user. Machine installation must not run the application as administrator.

The production database is `%APPDATA%\com.webswe.civildesk\civildesk.sqlite3`. A prior read-only observation reported schema v8; this milestone did not open or copy it. Before any production-identity launch, obtain owner authorization, stop all CivilDesk processes, make a consistent backup of the database **and SQLite WAL/SHM sidecars**, app settings, WebView2 profile, and project references, and verify that backup. Test v8→v9→v10 with synthetic fixtures and on a separately authorized backup copy. An older v8 application may not understand a migrated v10 database. Rollback therefore restores a matched application/database backup pair; never let an older binary open a migrated database. Migration failure must leave the original data available for restoration.

## Future supervised gates

1. Obtain separate owner approval for staging and confirm recoverable backups.
2. Rehash the independent source candidate and trusted manifest; require source `3ce164827ce10e6a311d4c4bdf6ecc9f7624c60f`, manifest SHA-256 `7c09cc6f3941ff86d20e779a2275269ba0f9a47cac28939779f3cc0108cf29db`, executable SHA-256 `fa06c5f1ab284130184715eb8b3ac04a61c5d07caa77ed44acb3f13bc1c46243`, 306 files, and 139,599,398 bytes. Hashes identify bytes relative to a trusted manifest; they do not prove publisher authenticity or a secure build chain.
3. In an elevated disposable VM, stage the separate CLI and manifest, apply protected ACLs, check parent directories and effective rights, and verify final paths and inventory again. Installation, ACL changes, and firewall changes require administrator privileges.
4. Build the CivilDesk per-machine candidate from reviewed source. The compile-time approval record, if separately authorized, must bind the exact canonical versioned root, independent manifest path and digest; the manifest binds source and executable identity and complete inventory. Reject relocated packages and legacy standalone settings. `APPROVED_FROZEN` stays `None` for this foundation milestone.
5. Sign the installer and application with a managed Authenticode identity, verify signatures and hashes through a trusted distribution channel, and protect the signing key separately. The current build has no production Authenticode identity; a hash without a trusted distribution chain is insufficient. Record signing and artifact provenance for revocation/rotation.
6. Apply an administrator-managed outbound firewall block to the exact installed `d2l.exe` path on all profiles, verify policy application under a non-admin token, and recheck after every versioned upgrade. A path rule does not contain child executables or copied binaries. For a strict offline guarantee, use a network-disconnected host or stronger OS isolation; an executable-specific rule is only a defense in depth control.
7. Verify HKCU/HKLM transition, backup and rollback, no active legacy standalone route, no vulnerable `9e0da75` fallback, restricted Scope A behavior, and no user-data loss in a disposable VM. Obtain separate owner approval before production activation.

## Revocation and limitations

Immediate operational revocation can deny read/execute on the separately managed package or remove it through a controlled elevated process, while preserving user data. A clean no-approval CivilDesk build is needed to remove a compiled approval without depending on filesystem absence; install it through the protected channel after separate review. Do not roll back to the vulnerable `9e0da75` package or re-enable standalone trust. Preserve legacy settings as inert data. Restore previous application/database state only from a verified matched backup. A package hash check and ACL policy cannot eliminate administrator compromise or the process-creation window before a job object attaches. Installer, multi-user ACL, firewall, signing, and v8 production-backup acceptance remain pending separately authorized tests.
