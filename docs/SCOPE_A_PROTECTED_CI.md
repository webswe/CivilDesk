# Protected NSIS build-only CI

The local development branch adds `.github/workflows/protected-installer-build.yml`. It runs only on a push to `verification/scope-a-protected-installation-foundation`, after separate owner authorization. The workflow has a read-only repository token and no manual dispatch, pull-request-target, release, upload, installer execution, elevation, credential, or firewall step. A new workflow need not first be merged into default-branch `main` for its branch-push trigger; manual dispatch is intentionally absent. Do not push as part of local development.

The ordinary `ci.yml` native job already runs on `windows-latest`, uses Node 24 with npm caching, the stable Rust toolchain, `swatinem/rust-cache@v2`, `npm ci`, and `npm run tauri build -- --bundles nsis`. It previously produced and hashed an ordinary NSIS installer. Tauri's bundler obtains its Windows NSIS toolset and required plugins in a tool cache, then invokes `makensis`; the Rust cache does not itself provide NSIS. The protected job uses the same toolchain and a distinct Cargo target directory (`src-tauri/target/protected`), with a matching Rust cache workspace. No installer is uploaded or retained after the ephemeral runner ends.

The protected job selects only `src-tauri/tauri.protected.conf.json`. The default config remains `currentUser`; the overlay requests `perMachine`, retains `com.webswe.civildesk`, and disables updater artifacts. The job checks the generated `installer.nsi` for the resolved install mode and identity, the administrator execution directive, the Program Files root, and the HKLM uninstall path. It also checks the installer filename and PE product/version metadata, computes SHA-256 for the generated NSIS script and installer, and copies the installer to a variant-labelled path **on the runner only**. `metadata.json` and the job summary record source SHA, variant, Tauri CLI version, architecture, filenames, hashes, and Authenticode status. The copied filename and isolated target path distinguish it from an ordinary build; the copied installer is neither uploaded nor released. This script verification is evidence of build configuration, not proof of installed behavior or publisher authenticity.

Local validation: parse the workflow YAML, run `node scripts/check-protected-ci.mjs`, `npm run check:protected-install`, and `./scripts/test-protected-installer-metadata.ps1`. The first remote run must be reviewed for the exact head SHA, successful NSIS build, generated-script checks, PE metadata, hash, and absence of artifact upload. A failure does not authorize a rerun, fix, or release. `APPROVED_FROZEN` remains `None` in this build.

## Later installation acceptance, separately authorized

Build-only CI cannot prove HKLM registration, elevation prompts, standard-user runtime, ACL effectiveness, package independence, firewall enforcement, migration, or rollback. A later disposable Windows runner could exercise synthetic installer installation and registry assertions, but meaningful multi-user isolation, snapshots, restoration, and protected package staging belong in a dedicated disposable VM. Keep that future workflow separate from build-only CI.

For the future VM: snapshot before each case; install the per-machine installer and check HKLM/Program Files; rehearse HKCU coexistence, upgrades, uninstall, and preservation of a **separately** staged synthetic package; test administrators versus standard users on application/package/manifest ACLs and writable ancestors; test symbolic links, junctions, hard links, and canonical paths; use a synthetic network executable and controlled endpoint to check an administrator-managed outbound block on all profiles; migrate only synthetic v8 databases, check integrity and foreign keys, then restore a matched application/database snapshot. Revoke by removing a synthetic manifest or package and by testing a no-approval build, never by selecting a legacy standalone executable. No real D2L-CLI, Credential Manager entry, Brightspace endpoint, production database, or Acceptance installation is part of these tests.

Owner decisions still required: authorize a dedicated verification-branch push; review the first remote build result; separately authorize any privileged disposable-runner or VM installation test; approve signing and trusted distribution before any deployment; and separately review any future compile-time Scope A approval record.
