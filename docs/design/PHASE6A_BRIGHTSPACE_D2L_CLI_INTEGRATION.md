# Phase 6A — Brightspace through D2L-CLI: architecture investigation

**Status:** design only, 6 November 2026. No CivilDesk or D2L-CLI behavior was changed; no live Brightspace command was run. **Verified** means observed in the two repositories at CivilDesk `fe5f349` and D2L-CLI `3758e02`. **Proposed** means a future implementation choice. The pending CivilDesk Windows CI and full native E2E verification on `84c02de`, followed by owner approval of implementation scope, is a prerequisite.

## 1. Executive summary

**Verified:** D2L-CLI 0.1.1 already provides a documented JSON subprocess interface for courses, assignments, grades, announcements, and a grouped overview. It retains manual SSO/MFA, uses Windows Credential Manager for a stored session, and restricts authenticated HTTP to same-origin HTTPS GET requests. CivilDesk has a local School workspace with semesters, courses, task-backed coursework, study blocks/sessions, and a calendar, but no Brightspace provider or native gradebook model.

**Proposed:** place Brightspace panels inside School and invoke a narrowly allowlisted D2L-CLI command set through CivilDesk Rust. Start with on-demand reads and a bounded in-memory snapshot after an explicit refresh. Do not create tasks, courses, grades, calendar events, or a SQLite snapshot in 6A/6B. The major prerequisite is credential isolation: D2L-CLI's current fixed vault key is shared by processes under the same Windows user, regardless of CivilDesk's Tauri application identifier. The saved session also lacks an origin binding. No real CivilDesk integration may read that entry; the approved profile/origin contract must be implemented and verified first. Native E2E must run a synthetic executable only. Real-account access also requires separate owner approval.

## 3. Verified D2L-CLI capabilities and limits

Sources: D2L-CLI `pyproject.toml`, `README.md`, `docs/MACHINE_INTERFACE.md`, `src/d2l_cli/{cli,auth_service,credentials,session_store,config,browser_auth}.py`, `src/d2l_cli/client/http.py`, provider/model modules and fictional-fixture tests. Version in package metadata is `0.1.1`; Python requirement is `>=3.11`. The repository documents Windows 10/11, `uv sync --locked`, and a separate Playwright Chromium installation. Its `d2l` console entry point is `d2l_cli:main`. No standalone Windows binary or CivilDesk sidecar packaging is present in the inspected repository.

**Confirmed operations:** manual `auth login`; network-verifying `auth status`; JSON courses list; course-scoped assignments, grades, and announcements; cross-course assignment overview; unified academic overview. `auth login` launches headed isolated Playwright Chromium for the person to complete SSO/MFA. The CLI does not collect a password or MFA code. `auth status` performs a course-list GET when a session exists; it is human-readable, not JSON. There is **no verified logout/disconnect command**. The CLI's public authenticated HTTP surface is GET-only, accepts relative targets under a plain HTTPS configured origin, checks the built request origin, verifies TLS, disables automatic redirects (with one validated, same-origin grades GET redirect), and bounds each response to 25,000,000 identity-encoded bytes. Assignment pagination that would require an unverified POST is not used; a course-list bookmark causes failure rather than partial success. Provider structure failures abort a command.

**Limits:** assignments may be omitted when no recognized link exists; a `null` due date means no positively recognized displayed date, not proof of no deadline. Due dates are timezone-naive ISO strings from the provider's display. Assignment submission status and score are uninterpreted strings. Grade fields are displayed strings or null; feedback is `none`, `present`, or `unknown` availability only, with no feedback text. Grade rows have **no verified stable item ID**. Announcements have sanitized plain-text title/body and a validated relative detail reference, but no date, author, read state, or verified recency. Announcement body is complete sanitized text from the listing, not merely the 120-character terminal preview. Unified overview fails as a whole if a provider read fails; it does not produce a silently partial JSON success.

## 4. Exact command and process contract

The supported machine interface lists these **exact** JSON invocations. From a checkout, D2L-CLI documents `uv run d2l` in place of `d2l`; a CivilDesk adapter must launch an approved executable directly with an argument vector, never a shell command.

| Invocation | JSON stdout envelope | Scope/flags |
| --- | --- | --- |
| `d2l courses list --json` | `{"courses":[COURSE,...]}` | Provider order. Non-null bookmark fails. |
| `d2l assignments list --course <id> --json --include-completeness` | `{"assignments":[ASSIGNMENT,...],"completeness":ASSIGNMENT_COMPLETENESS}` | `<id>` is numeric course/org-unit ID. Completeness flag is optional in CLI; adapter should require it. |
| `d2l assignments overview --json --include-completeness` | `{"assignments":[OVERVIEW_ASSIGNMENT,...],"course_completeness":[COURSE_COMPLETENESS,...]}` | Optional `--chronological` and `--all-courses`; reduced records omit submission status/score. |
| `d2l grades list --course <id> --json --include-completeness` | `{"grade_items":[GRADE_ITEM,...],"completeness":"unknown"}` | Preserves visible provider order. Completeness flag is optional in CLI; adapter should require it. |
| `d2l announcements list --course <id> --json --include-completeness` | `{"announcements":[ANNOUNCEMENT,...],"completeness":"unknown"}` | `--details` changes human output only, so adapter omits it. |
| `d2l overview --json` | `{"courses":[ACADEMIC_COURSE,...]}` | Optional `--all-courses`; default active accessible courses. JSON always contains full retrieved records and per-source completeness. |

`d2l auth login` is interactive and writes the CLI's session credential after manual SSO/MFA; `d2l auth status` is human text of the form `<state>: <detail>` with states `authenticated`, `not_authenticated`, `stored_session_unreadable`, `session_expired`, `storage_unavailable`, or `provider_unavailable`. It makes a real read when a session exists. These two commands are **not** JSON contracts. There is no supported machine-readable auth-status envelope; parsing the human detail as a stable protocol would be unsafe. Real CivilDesk integration requires the proposed versioned JSON auth contract below; an older CLI must fail compatibility negotiation rather than fall back to human-text parsing.

Process behavior: exit `0` means complete JSON object plus newline on stdout (empty lists are valid); anticipated auth/storage/provider/validation failures exit `1`, leave stdout empty, and write a safe `error:` message to stderr; usage errors exit `2`. Warnings may appear on stderr even with successful JSON. Consumers check exit code before parsing stdout and do **not** parse warning prose as completeness metadata. Object-key order is not contractual; array order is. Current `docs/MACHINE_INTERFACE.md` and tests pin exact keys and nullability through 0.1.1, so this is suitable as a version-pinned machine contract, subject to runtime limits and deliberate compatibility review when D2L-CLI changes.

Additional keys require deliberate version review, consistent with the CLI's exact-key tests.

## 6. Authentication, credential ownership, and identity

**Verified:** `auth login` waits for manual SSO/MFA in a temporary browser context, then `SessionStore` serializes `cookie_header` and `cookie_names` into `keyring` service `d2l-cli`, key `session`. `KeyringCredentialStore` accepts only `keyring.backends.Windows.WinVaultKeyring`; it fails rather than using plaintext fallback. The session payload does **not** include the configured origin or a Brightspace account ID. `D2L_CLI_BASE_URL` defaults to `https://kennesaw.view.usg.edu/` and can be overridden by environment variable; the CLI validates it as a plain HTTPS origin, but the stored cookie is not keyed to that origin. The current CLI has no supported authenticated-user identity command. Credential Manager protects the entry per Windows user, **not per CivilDesk production/Dev/Acceptance/E2E identity**.

| CivilDesk identity | Verified Tauri identity | Proposed access policy before CLI isolation exists |
| --- | --- | --- |
| Production | `com.webswe.civildesk` | Real CLI access only after explicit owner opt-in and credential/origin isolation gate. |
| Dev | `com.webswe.civildesk.dev` | Synthetic adapter or separate Windows user; never silently share production CLI credential. |
| Acceptance | `com.webswe.civildesk.acceptance` | Synthetic adapter or separate Windows user; no automatic real session access. |
| E2E | `com.webswe.civildesk.e2e` | Synthetic executable only; hard fail if configured path resolves to real CLI or production credential namespace. |

**Proposed connection flow:** settings in School (or a small integration card in Settings) records an approved CLI installation and institution origin as nonsecret configuration. “Connect Brightspace” clearly launches the CLI's `auth login` in an interactive user-visible flow; CivilDesk never asks for credentials. A status check must verify provider acceptance, not mere vault presence. A rejected session offers “Sign in again” without asserting the cause; reauthentication repeats manual login. Refresh is user initiated. “Disconnect from CivilDesk” disables the adapter and clears only CivilDesk's short-lived in-memory academic data; it **cannot claim to delete D2L-CLI's stored session** because no CLI logout command exists. Offer a separate, explicitly scoped CLI-managed sign-out only after such a command and credential namespace are designed and approved. Never reach into the CLI vault entry from CivilDesk.

**Security prerequisite:** before any real integrated use, D2L-CLI needs an owner-approved mechanism to bind stored session material to both the exact HTTPS origin and a consumer/identity namespace. The current fixed service/key and mutable origin environment are insufficient. CivilDesk must not improvise a credential key via unsupported flags, read the vault itself, or assume Tauri IDs solve this. If a real account identifier cannot be obtained through a supported CLI contract, show the configured institution and “account identity not verified”; do not infer identity from course names or a token. A future trusted machine-readable auth status/origin report would simplify this, but is not present today.

## Credential Isolation and Authentication Contract

This section refines the prerequisite above. **Verified** statements describe D2L-CLI at `3758e02`; names, commands, fields, and policies labeled **proposed** do not exist yet. Nothing here authorizes reading or migrating the owner's existing vault entry.

### Verified current credential behavior and threat model

- `KeyringCredentialStore` calls `keyring.set_password`, `get_password`, and `delete_password` with service `d2l-cli` and the caller's key. `SessionStore` always supplies key `session`. This is the exact keyring tuple visible in source; the WinVault backend's internal Windows target-string formatting is outside the inspected code. Only `keyring.backends.Windows.WinVaultKeyring` is accepted; backend failure has no plaintext fallback.
- The legacy JSON payload has exactly `cookie_header` and `cookie_names`. It contains neither origin nor profile nor user identity. `SessionStore.load()` validates the serialized length and field shapes, but cannot compare an origin. Its `clear()` method deletes `session`; no public logout command or automatic clear path was found in the CLI. A new successful login overwrites the same entry.
- `D2L_CLI_BASE_URL` (default `https://kennesaw.view.usg.edu/`) is read on each CLI process. `auth login` checks vault availability, opens a separate headed Chromium context, waits for manual SSO/MFA and return to the configured origin, captures cookies for that origin, then saves them. Read commands load the same fixed session and provide its Cookie header to a new client configured from the *current* base URL. No payload-to-origin comparison occurs before that header is returned.
- `auth status` is human text only. With a stored session, it verifies through a course-list GET. `authenticated` means that live read succeeded. Its `session_expired` state also covers permission denial, so it does not prove a cookie's age or that reauthentication alone will fix access. `provider_unavailable` groups network, TLS, and other provider errors; `not_authenticated`, `stored_session_unreadable`, and `storage_unavailable` are locally observable. An in-progress login and a specific Brightspace account identity are not observable from the current status command.
- The HTTP client validates a plain HTTPS origin, accepts only relative authenticated request paths, checks the built request's origin before sending, uses TLS verification, and has no automatic redirects. Grades have one explicitly validated same-origin GET redirect path. Browser-owned SSO redirects are separate from authenticated API requests. The existing request boundary prevents a request target from redirecting a cookie to a different origin, but a changed `D2L_CLI_BASE_URL` can still cause the *unbound stored cookie* to be offered to a different configured portal. Cookie scope in the browser does not repair that later CLI reuse.

**Threat:** any process running as the same Windows user with access to this CLI and its vault entry can select the legacy key. CivilDesk production, Dev, Acceptance, and E2E Tauri IDs do not create Windows Credential Manager process namespaces. A misconfigured CivilDesk adapter, another local consumer, or a mutable environment could reuse the owner's standalone session or direct it at the wrong portal. A profile separates accidental consumers and origins; it is not a security boundary against malicious code already running as that Windows user. Executable trust, constrained process invocation, and OS account security remain necessary.

### Proposed versioned credential profiles

Introduce an additive **v2** profile contract in D2L-CLI, with immutable machine IDs and an explicitly configured canonical portal origin. Reserve `standalone`, `civildesk-prod`, `civildesk-dev`, `civildesk-acceptance`, and `civildesk-e2e-synthetic`; the last is a protocol/test identity only and must never authorize a real vault session. Each real profile has its own vault entry for each exact origin. A friendly institution name is display metadata, never a key or proof of account identity. An origin change requires a different credential entry and fresh authentication, not rebinding an existing session.

**Proposed target construction:** validate a registered ASCII profile ID against `^[a-z][a-z0-9-]{0,39}$`, then compute `SHA-256(UTF-8("d2l-cli/session/v2\0" + profile_id + "\0" + canonical_origin))`, where `\0` denotes a NUL separator byte. Store with keyring service `d2l-cli/v2` and key `session/<profile_id>/<64 lowercase hex digest>`. The domain separator, full digest, and distinct service avoid collision with the legacy `d2l-cli` / `session` tuple; inputs are nonsecret. A v2 JSON credential includes `format_version: 2`, `profile_id`, `portal_origin`, `cookie_header`, and `cookie_names`, with strict size and type validation. Compare profile, origin, and format to the selected configuration **before** returning a Cookie header or starting any authenticated request; mismatch or malformed payload fails closed. Treat unexpected target collision as corruption, never as a usable session. Do not log the payload or cookie names. Protect it with the existing trusted WinVault backend requirement.

**Proposed selection:** D2L-CLI accepts a nonsecret, explicit profile selector and explicit portal-origin configuration on its approved commands (exact flag spelling is an implementation contract to settle in D2L-CLI, not a current CLI capability). CivilDesk Rust supplies only its fixed build-identity profile and configured origin through structured arguments or a tightly controlled child environment. Neither contains a credential secret. Validate IDs and origin in both programs; the CLI must reject unregistered/malformed IDs, missing origins for v2, and conflicting `D2L_CLI_BASE_URL` rather than silently selecting another origin. CivilDesk must reject `standalone`, legacy mode, and profiles belonging to a different CivilDesk identity. Do not treat a user-editable profile string or environment variable as authorization. E2E uses a fake executable and never invokes a real CLI with `civildesk-e2e-synthetic`.

### Proposed portal-origin binding

Canonicalization must happen once at the CLI config boundary and be reused by browser login, vault lookup/payload validation, and the GET client. Require HTTPS and a plain origin: no userinfo, query, fragment, path beyond `/`, whitespace, percent-encoded host, IP literal, `localhost`, Unicode hostname spelling, trailing dot, empty/double labels, or ambiguous numeric host. Accept a normalized ASCII DNS A-label host only after label-length and syntax checks; lowercase it and normalize an explicit `:443` away. Use the canonical `https://host[:port]` as the equality value. For real profiles, default to port 443; any nonstandard port needs an explicit, reviewed policy before release. Reject invalid input instead of repairing it silently. This stricter policy is **proposed**; current `_parse_base_url` is not the complete v2 policy.

For every v2 command, compare (1) selected profile configuration, (2) target-derived origin, (3) decrypted payload origin, and (4) actual request origin. A changed portal never falls back to another target or to the legacy entry. Without an entry at the new origin's target, report `authentication_required`; do not claim to have detected another portal's credential. Validate before exposing a Cookie header. A stored credential for portal A must not be offered to portal B even when B is a valid HTTPS origin. During interactive login, allow the user's browser to visit the institution's SSO/IdP domains, but capture only cookies scoped to the configured Brightspace origin after return. Keep authenticated CLI requests GET-only, relative-path-only, TLS-verified, and with automatic redirects disabled; preserve only the grades provider's specifically validated, same-origin one-redirect GET. Do not let an SSO redirect become an authenticated cross-origin API follow.

### Legacy-session compatibility and migration

Keep existing unqualified standalone commands and the legacy `d2l-cli` / `session` entry unchanged for current consumers until an explicit compatibility/deprecation decision. The legacy format has no verifiable origin binding; document that residual risk for standalone use. CivilDesk must **never** select, probe, copy, delete, or auto-adopt it. An opt-in v2 standalone profile should use a fresh login and an origin-bound entry. Do not enumerate legacy credentials to discover accounts. An optional future migration would require informed user consent, an independently verified origin/account binding or fresh sign-in, and a documented rollback; a mere environment URL or successful token read is insufficient proof. No migration is part of Phase 6A design.

**Existing-consumer compatibility:** D2L-CLI's `docs/HAVILAND_INTEGRATION.md` records Haviland as a subprocess consumer with five fixed read-command argument vectors and schemas that reject extra JSON fields. This is verified from D2L-CLI documentation, not a fresh audit of Haviland's repository or runtime. The v2 profile selector, contract query, and JSON auth status must be opt-in additions: the existing five commands, JSON envelopes, human `auth status`, exit behavior, and default legacy credential lookup must remain compatible until each consumer explicitly migrates. Do not add even optional fields to Haviland's existing JSON records without coordinated schema changes and tests. Haviland continues to face the legacy origin-binding risk while it uses the old entry; this design does not change Haviland or silently make its session safe. CivilDesk negotiates v2 independently and cannot use Haviland's compatibility mode as a fallback.

### Proposed authentication and compatibility contract

Add a versioned, offline capability query (for example, `contract --json`) and a v2 JSON mode for `auth status` and login outcomes. These are **proposed commands**, not flags supported at `3758e02`. Preserve current human output and exit behavior for unqualified standalone commands. CivilDesk requires a known major contract version and explicit `credential_profiles_v2`, `origin_binding_v2`, and `auth_status_json_v1` capabilities **before** permitting a real login or read. An older or unknown CLI returns `unsupported_cli_contract`; never fall back to legacy key selection or human-output scraping. Future minor versions may add fields only under a documented negotiation rule; unknown security-critical semantics fail closed.

The proposed status JSON is one bounded UTF-8 object with `contract_version`, `profile_id`, `portal_origin`, `state`, `verification` (`local`, `live`, or `none`), `checked_at` (ISO timestamp or null), `error_code` (stable safe code or null), and `message` (short sanitized display text). It contains no cookie, cookie name, token, student record, or raw provider response. A successfully formed status report may exit `0` even when sign-in is needed; malformed configuration, unsupported contract, or process failure uses a nonzero exit with a structured safe error. The precise exit table belongs in the new CLI machine-interface specification and tests. CivilDesk validates the envelope, version, selected profile, and origin before using a result.

| Proposed state | Evidence and safe interpretation |
| --- | --- |
| `not_configured` | No valid v2 profile/origin configuration; local check only. |
| `authentication_required` | No credential at the selected v2 target; local check only. |
| `authenticated` | The selected credential passed origin/profile validation **and** a live provider GET succeeded. Vault presence alone is insufficient. |
| `session_rejected` | Provider rejected/denied the live verification; current CLI calls this `session_expired`, but actual expiry versus revoked access/permission cannot be distinguished. Offer sign-in or support, not a definitive expiry claim. |
| `portal_mismatch` | Payload, target, requested origin, or resolved request origin disagree; stop before authenticated network I/O. Never auto-rebind. |
| `credential_access_failure` | Trusted WinVault backend unavailable or v2 entry unreadable/corrupt; include a safe error code, not vault details. |
| `provider_unavailable` | Verification could not establish acceptance because of network, TLS, or provider error; show unknown authentication state, not authenticated or expired. |

`authentication_in_progress` is CivilDesk Rust's transient child-process state while interactive login runs; it is not a persisted CLI status. `authentication_failed` is a sanitized login-operation result after cancellation, timeout, or SSO failure, not evidence of a particular stored-session state. The current CLI cannot reliably identify the Brightspace account, distinguish session expiry from authorization denial, or prove auth while offline. Do not invent those claims. A future structured error envelope for **read commands** is also needed if CivilDesk must distinguish auth rejection from other nonzero exits; until then, report generic read failure without parsing human stderr. On login success, status still needs a live verification before the UI says authenticated.

### CivilDesk Rust adapter and E2E isolation

Only a trusted, pinned executable may be launched. Rust selects the profile from CivilDesk's production/Dev/Acceptance app identity and never accepts a profile, executable path, argument vector, or portal URL from arbitrary WebView command input. Portal configuration is validated and held as nonsecret local settings. Restrict operations to the negotiated auth/status and GET-only read allowlist; pass structured arguments without a shell; explicitly set the child environment so inherited `D2L_CLI_BASE_URL`, Python, keyring, proxy, or test overrides cannot silently change the selected origin or code path. Recheck executable trust at launch. Bound stdout/stderr while streaming, enforce separate read/login timeouts, kill process descendants on cancellation, validate JSON strictly, and return fixed sanitized errors. Do not log child output, profile payloads, cookies, or student records. CivilDesk disconnect disables its adapter and clears in-memory data; it does not delete a CLI credential. Any future profile-specific CLI sign-out requires a separate explicit contract and owner decision.

E2E must launch a dedicated deterministic synthetic executable from the isolated `com.webswe.civildesk.e2e` build. It must not start the real D2L-CLI binary or call Windows Credential Manager for a Brightspace session, even under the synthetic profile name. Static guards should reject real CLI paths, standalone/production profile selectors, a real portal origin, and credential-store imports in the test adapter. Runtime guards should assert the resolved executable identity and path, E2E app ID, synthetic origin, and child environment before spawning; fail closed if any differs. Synthetic tests should attempt a forbidden profile/portal switch and assert rejection before child launch. Run them with fictional records and no real credentials. Tauri app-ID isolation remains useful for CivilDesk's own data, but does not isolate another process's vault.

### Implementation sequence and acceptance criteria

1. Specify and test the additive D2L-CLI v2 profile/origin/status contract offline with fake keyring and HTTP/browser boundaries. Keep legacy tests and public commands passing. Do not touch existing credentials during development tests.
2. Implement profile-specific login, load, and optional explicit sign-out in D2L-CLI only after its owner approves the contract. Test target determinism, cross-profile and cross-origin denial, malformed IDs/origins/payloads, no Cookie header or network access on mismatch, SSO cookie capture, and the GET/redirect boundary.
3. Implement CivilDesk contract negotiation and restricted Rust adapter, then synthetic native E2E for all CivilDesk identities and failure paths. Verify old CLI refusal, no access to the legacy key, no real executable from E2E, bounded/cancelled processes, and sanitized logs. A real-user sign-in is a separate, explicit acceptance activity, never an automated test.

**Security acceptance gate:** a fresh CivilDesk production profile cannot read a standalone, Dev, Acceptance, E2E, or different-origin session; all mismatch checks occur before a Cookie header is emitted; offline status never claims authenticated; a known-good live GET is required for that state; old CLI versions cannot enter the real adapter; E2E cannot reach a real CLI or credential vault; legacy standalone functionality and its entry remain unchanged. Review these in code and tests before any real Brightspace account is connected.

**Remaining owner decisions:** approve the additive D2L-CLI v2 contract and separate repository work; decide whether/when to deprecate the origin-unbound legacy standalone mode; approve policy for nonstandard portal ports, if needed; decide whether a future profile-specific sign-out deletes its credential or CivilDesk disconnect remains local only. The actual Brightspace account identity cannot be established from today's CLI and must stay explicitly unverified unless a future supported identity contract is developed.

## 7. Proposed Rust adapter and trust boundary

```
School UI → allowlisted Tauri commands → Rust Brightspace adapter
          → approved D2L-CLI executable → configured Brightspace HTTPS origin
```

Only Rust may spawn the executable. Do not grant the WebView a general shell or arbitrary-process capability. A command enum should expose narrowly: `CourseList`, `AssignmentList(courseId)`, `GradeList(courseId)`, `AnnouncementList(courseId)`, optionally `AssignmentOverview`/`AcademicOverview`, `AuthStatus`, and the explicit interactive `AuthLogin` flow. Build a fixed argument vector for each variant; validate course IDs as ASCII digits with a small length cap; never pass a raw command, URL, executable path, or arbitrary flags from frontend parameters. No shell interpolation.

Use a canonical absolute path selected through a trusted installation flow; reject network/UNC paths, symlinks/reparse surprises, user-writable download/temp locations, and paths outside an approved install root. An external Python entry-point launcher is not enough proof by itself: its interpreter, package, dependencies, and scripts must also be trusted and pinned. Validate publisher signature or pinned digest of the entire distribution and version/contract metadata where available; recheck at launch to limit path substitution. For a future bundled binary, resolve it from the application resource directory and verify the signed/packaged payload. A hash or signature validates bytes/publisher, not their access to the shared vault; credential isolation remains separate. The exact Windows trust policy needs a packaged prototype before release.

Launch with `std::process::Command` or a Rust-only Tauri sidecar API using structured arguments, a restricted environment (especially controlled `D2L_CLI_BASE_URL`, Python/Playwright/keyring override variables, PATH, and proxy variables), a known working directory, no inherited stdin for reads, and separately captured stdout/stderr. An interactive login needs a visible browser and a separate longer timeout; never use a hidden `Start-Process` helper for the user's SSO window. Bound both streams while reading (not after buffering), set per-command wall-clock deadlines, cancel/kill the child and its descendants on navigation or explicit cancel, and reject truncated or oversized output. Initial **proposed** limits: 60 seconds and 4 MiB stdout for a course-scoped read, 2 MiB stderr, with a separately budgeted overview and a roughly 11-minute interactive-login ceiling matching the CLI's 600-second browser wait. Tune only using synthetic worst-case tests. At most one refresh at a time; avoid a burst of processes across many courses.

On exit `0`, require one UTF-8 JSON object, the correct envelope, exact expected fields/types, valid course associations and unique source IDs, count consistency, and supported completeness values. Reject extra top-level/record fields until reviewed for contract change. For today's JSON read commands, nonzero exit means empty stdout; classify timeout, invalid contract, oversized output, and cancellation from the adapter's own observations. Parse a nonzero auth or read error envelope only if a future negotiated contract explicitly defines its shape and exit code. Otherwise return a generic failure. D2L-CLI's current JSON read commands return human `error:` stderr rather than structured error codes, so do not scrape arbitrary prose. Never log captured stdout/stderr, cookies, course IDs, URLs with queries, or student text. Return fixed user-safe errors and retain detailed diagnostics only as non-sensitive categories.

## 8. Installation and packaging analysis

| Approach | Development | Production implications |
| --- | --- | --- |
| External D2L-CLI | Best for an isolated prototype: independently pinned D2L checkout/venv or future signed executable, explicit local path, no CivilDesk installer change. | Current documented install requires Python 3.11+, `uv`, locked dependencies, and a separate Chromium download. A simple `d2l.exe` entry-point launcher still depends on Python and packages. Unmanaged upgrades and mutable paths weaken executable trust and contract pinning. Not acceptable as an effortless end-user install today. |
| Bundled sidecar | Not needed to prove the adapter. | Tauri 2 supports `bundle.externalBin` and Rust-side sidecar execution; binaries need target-triple naming. A frozen Windows D2L-CLI could bundle Python so testers need no manual Python install, but Playwright Chromium and its driver/resources must also be packaged or reliably provided. This increases NSIS size, build time, code-signing scope, and update coupling. No frozen build or installer smoke test was found, so feasibility and actual size remain unverified. |

**Recommendation:** use a pinned external CLI in development **only with synthetic data or a separately isolated OS account** until credential/origin isolation exists. For production, aim at a signed Windows sidecar built from a pinned D2L-CLI release and a tested Chromium package, delivered in CivilDesk's NSIS installer; retain an external-install option only for advanced, explicitly approved setups. A PyInstaller `onedir` prototype is easier to inspect/debug than a one-file bundle; compare startup, signing, antivirus behavior, browser launch, and installer size before choosing. This is feasible in principle, not proven for this repo. Tauri's [external-binary guide](https://v2.tauri.app/develop/sidecar/) documents `externalBin` and target-triple naming; [PyInstaller's operating-mode guide](https://pyinstaller.org/en/stable/operating-mode.html) documents bundling the interpreter; [Playwright's Python guide](https://playwright.dev/python/docs/library#pyinstaller) documents PyInstaller/browser bundling, and its [browser guide](https://playwright.dev/python/docs/browsers#managing-browser-binaries) describes the separate browser cache. These are packaging references only; no sidecar was built in this investigation.

## 9. Proposed School experience

Keep the existing School overview, semester/course navigation, local coursework, and Study view. Add a clearly labeled **Brightspace** source section within School, with a small connection/refresh control rather than a new top-level sidebar item. Do not mix provider rows into the local task completion counts. Show local and Brightspace course cards separately until an explicit course association exists.

- **School overview:** active accessible Brightspace courses, upcoming assignments with recognized due values, visible-grade summary as *counts of retrieved items* rather than calculated performance, announcement titles/previews in provider order, last successful refresh, and per-source completeness/error/stale labels. If no local semester exists, provider browsing still works; no local semester is silently created.
- **Course detail:** Brightspace assignments, read-only grade items, announcements, and local study activity only if the user later explicitly associates this Brightspace course with one local course. Before association, show study activity as unavailable rather than matching on a code/name guess.
- **Assignments:** display provider name, raw `submission_status`, raw `score`, and the timezone-naive due date/time as “Brightspace displayed time; timezone unknown.” `null` is “Due date not shown or not recognized,” never “No deadline.” Do not infer completion from grade or status text; show “Completion not verified.” Avoid overdue/due-soon labels that require a verified timezone/clock interpretation. No automatic local task creation.
- **Grades:** show exact `displayed_points`, `displayed_grade`, and `displayed_weight` strings, each blank as “Not shown”; feedback availability only. No zero substitution, GPA, weighting, average, or grade-to-assignment join. Do not offer a durable grade-item link until a stable ID exists.
- **Announcements:** render sanitized plain text as text, keep course attribution, do not execute `detail_reference`, and do not label the first item “latest” without a date. Show short bodies by default and expand in memory on demand; no notification or full-body persistence.

## 10. Freshness, completeness, identity, and provenance

Treat each refresh as a *read attempt*. Per course/source record `attemptedAt`, `lastSuccessfulAt`, `sourceError` category, and `coverage`. The last successful value is in memory only in 6A/6B and disappears on restart. If a new read fails, the old in-memory snapshot may remain visible with a prominent **stale** marker and its successful timestamp; never replace it with an empty success. A restart with no cache shows “Not refreshed yet.” A successful empty array is distinct from error and from missing source access. Do not perform background polling or automatic startup requests.

For assignments, keep the CLI's `below_page_size_boundary`, `potentially_truncated`, or `unknown` **per course**. The first means only that observed rows were below a selected page-size boundary, not that all assignments are guaranteed retrieved. `potentially_truncated` must warn that more work may exist. Grades and announcements remain `unknown`. Unified overview counts are retrieved counts, not course totals. A failure from `overview --json` invalidates that entire attempt; course-scoped reads may keep independently successful sections with section-specific errors. Cap selected courses/processes and mark omitted courses “not fetched” rather than silently excluding them. Date-null and grade-null meanings remain separate from completeness.

Source provenance key for in-memory rows is the configured **HTTPS origin plus CLI credential namespace/account context when available**, and provider course ID. Assignment key adds `id`; announcement key adds `announcement_id`. Grade items have no durable provider ID, so only a per-refresh presentation row/index is possible, explicitly ephemeral and never a deduplication key. Reject duplicate source IDs and cross-course associations rather than overwriting. The CLI does not expose an authenticated account ID today: source origin and vault namespace do not prove a person. Show that limitation, and never use course code/semester name as identity.

## 11. Persistence strategy and future relationships

**Initial recommendation:** on-demand reads with a short-lived, size-bounded, process-memory cache during the running CivilDesk session. Only nonsecret CLI path/origin/opt-in configuration may persist if the security gate is met. No v11/v12 migration for Brightspace academic data, no snapshot of raw student records, and no import into `courses`, `task_academic`, `tasks`, `calendar_events`, or grade tables. Disconnect clears in-memory Brightspace data; it never deletes local coursework or the CLI vault entry.

If later explicit snapshots are approved, use a separate Brightspace namespace/table with source origin, credential/account identity (if later available), course ID, assignment/announcement IDs, fetched/validated timestamps, CLI contract version, per-source completeness and stale state, and explicit retention/deletion rules. Preserve raw timezone-naive due text and nulls. Grade rows need a verified stable ID before durable per-item provenance; until then, snapshot only a bounded course-level display if approved, with no identity-based update semantics. A future 6C course association should be an explicit `(origin, Brightspace course ID) → local course ID` mapping and require review if either side changes; it must not create or complete coursework by itself. Avoid speculative generic provider tables in 6A.

## 12. Relationship to Notion

Share only small presentation concepts: source label/identity, connected/auth-required/offline state, last successful refresh, completeness/partial warnings, and clear provenance. Notion's data-source IDs, typed property mappings, Windows credential service, and read allowlist are separate from D2L-CLI's course/assignment contracts and vault entry. The approved Phase 5B design remains untouched. No common integration framework is justified by these two different boundaries today.

## 13. Security boundaries

Allowed future operations are manual CLI login/status, restricted GET-derived reads, local nonsecret configuration, and clearing in-memory views. Disallowed: assignment submission, grade editing, announcement posting, Brightspace content mutation, automatic task/course/calendar creation, sync, background polling, access to unrelated credentials, or raw student data in logs. Frontend inputs cannot select a process or arbitrary argument. The Rust adapter must maintain process/output limits, executable trust, exact JSON validation, and account/origin isolation; the CLI must retain HTTPS, TLS verification, GET-only methods, relative-path origin checks, disabled redirects, and bounded responses. A GET-only client narrows behavior but does not prove that the saved session itself has read-only privileges. Announcement plain-text sanitization does not make content trusted instructions; render as inert text.

## 14. Synthetic testing strategy

Use a synthetic D2L-CLI executable or injected process runner with the documented JSON envelopes and fictional courses. The native E2E binary must accept only this test executable, with an explicit build guard analogous to the isolated Notion mock; its credential namespace must never resolve to the real `d2l-cli/session` entry. No automated test invokes real login/status/reads, and no owner's Brightspace data appears in fixtures.

Unit/adapter cases: trusted path selection, missing/untrusted/changed executable, altered dependency root, wrong origin, forbidden command/argument, duplicate IDs, cross-course association, exact schema/Unicode/null handling, authentication required/session rejected/unknown, secure-store failure, offline/TLS/provider failure, exit 1/2, warning on successful stderr, timeout/cancellation/process-tree cleanup, malformed/oversized/truncated JSON, and refusal to parse partial output. Provider-view cases: assignment coverage states and missing due values, naive time preservation, unknown completion even with score, null/zero grade distinction, absent grade-item identity, feedback availability, announcement sanitization and no inferred recency, partial source refresh, stale cache, empty success, and restart clearing cache. Security tests assert no shell, no arbitrary executable/args, no real vault access in Dev/Acceptance/E2E synthetic tests, no domain-table writes, no Notion regression, and no outbound Brightspace traffic from synthetic E2E. Test that existing Haviland command envelopes retain their required keys, types, and nullability unless a separately coordinated consumer change is approved. Real account acceptance, if ever approved, is separate and manual.
